## Key Decisions Made (in the previous chat; open to revisiting)
- Build on GitHub Actions so client PCs never need Rust. The dev PC now has Rust for fast iteration.
- Use an NSIS per-machine installer for clients, with the MSI kept only as a fallback.
- For the Transfer Monitor (answers the user gave in the planning Q&A):
  - it supports both *Copy* mode (OpenDiff copies) and *Watch* mode (another tool copies, reconciled against a source manifest)
  - targets are local, USB and network drives
  - verification is size + date, with an optional hash
  - it copies only, never moves
  - it produces an exportable report
  - finish smoke-testing before building it
- The bundle identifier and upstream URLs were deliberately left unchanged. Changing the identifier moves the app-data location. That may need a fresh look now that there's a new product repo.

## Notes Claude Is Adding (not discussed in the original conversation)
- **Unknowns come first.** Neither altWinDirStat nor the Claude-built app was inspected: language, framework, build system and size are all unknown. Whether they can share one app shell (OpenDiff's Tauri/Vue) or stay as separate apps in one repo decides almost everything else.
- **"Merge" can mean different things:**
  - a monorepo with several apps side by side (`apps/opendiff`, `apps/altwindirstat`, …) and one CI
  - folding features into OpenDiff as new modes. It already has a mode system; adding a mode touches about 12 files.
  - a new app that uses parts of each

  These differ a lot in effort. Asking the user which they mean saves rework.
- **Git history is a real choice.** OpenDiff carries hundreds of upstream commits and 370 branches. Importing it as a plain copy, as `git subtree` with history, or as a submodule affects repo size, clone time, and whether upstream OpenDiff fixes can still be pulled in later.
- **License check.** OpenDiff is an open-source upstream project (license not checked in the previous chat). Combining it with other code, and shipping to clients, means checking that license and those of the other two projects.
- **One installer or several.** The current NSIS hooks, the Explorer menu keys (`OpenDiff`, `OpenDiffSelectLeft`), the bundle ID and `upgradeCode` are all OpenDiff-specific. A combined product likely needs new identity values, so a new install doesn't collide with or orphan the already-installed OpenDiff (uninstall the old one first?).
- **Rethink the Transfer Monitor's home.** It was planned for OpenDiff's crate layout. altWinDirStat, being a disk-usage tool by its name, may overlap with its scanning and manifest needs, and a shared scanner could serve both.
- **Split between GitHub and local builds.** GitHub Actions minutes, artifact retention and storage (the upstream release workflow has storage-pruning logic) matter once three apps build there. Local final builds also produce unsigned binaries, which Smart App Control may block differently from CI builds. Deciding where signing happens is part of this.
- **Unfinished items on the old fork.** PR #4 unmerged, PR #3 open, the branch cleanup and the unexamined `installer2.zip` are all still there. Settling them first, or deciding to leave the old fork frozen, avoids two sources of truth.
